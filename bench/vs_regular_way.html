The regular way, built fairly

Each regular method reads the same documents the Lean checker reads and respects what the sheet says about installed options, so none of them confuses a brochure option with the installed machine. Each one is a step closer to CryoLean. The code is bench/regular_way.py.

Spec-sheet checklist

  • one datasheet line at a time
  • a blank line passes
  • any number on the sheet is believed
  • no coupled physics

Careful spreadsheet

  • one line at a time
  • a blank line means "TBD"
  • any number on the sheet is believed
  • no coupled physics

Physics-aware script

  • lines plus heat budget, Joule heating, ramp time
  • a blank line means "TBD"
  • any number is believed
  • floats, no validity range

CryoLean

  • lines plus physics, exact rationals with units
  • a blank line means NEED INFO, and names it
  • only sourced numbers decide
  • every verdict backed by Lean theorems

What “correct” means

Correct means CryoLean's answer matches a specification written separately from the checker, in lean/CryoLean/Spec.lean. The two share only the record lookup, the exact rational order and exact arithmetic. Lean proves the match in both directions: verdict_accept_iff says CryoLean answers YES exactly when AcceptSpec holds, verdict_reject_sound and verdict_reject_complete say it answers NO exactly when RejectSpec holds, and NEED INFO is everything else. The specification is built in four layers.

  1. ValueMeets: one documented number meets one requirement. Every numeric case carries a unit check as a premise (d : m.dim = q.dim), so tesla is never compared with kelvin, and the comparison is exact: Q.le a b is a.num × b.den ≤ b.num × a.den on integers.
  2. SatisfiesKey: the number counts only if it belongs to the installed configuration and has a trusted source (manufacturer specification, measurement, reference data, a certified simulation, or the user's own entry). The one other way to satisfy a line is a trusted record that an option is not fitted, and only when the experiment needs that item absent. Estimates and unsourced records never count.
  3. ReqOK and CoupledOK: every mandatory requirement passes on some alternative key or is ruled out by a definitely false condition, and every coupled physics relation holds inside its validity range (for example, wiring heat load at most the cooling power documented at a temperature no warmer than the operating point).
  4. AcceptSpec: the profile is confirmed, all of the above holds, and at least one item genuinely passes. RejectSpec mirrors it with ValueFails: some mandatory item is violated by trusted evidence on every alternative.

Layer 1, as written in the specification

/-- "documented value `v` meets constraint `k`" -/
inductive ValueMeets : Constraint → CapValue → Prop
  | pointWithin {q lo hi : Quantity} (d₁ : lo.dim = q.dim) (d₂ : hi.dim = q.dim)
      (h₁ : Q.le lo.val q.val) (h₂ : Q.le q.val hi.val) : ValueMeets (.pointWithin q) (.range lo hi)
  | rangeWithin {rlo rhi lo hi : Quantity} (d₀ : rlo.dim = rhi.dim) (d₁ : lo.dim = rlo.dim)
      (d₂ : hi.dim = rlo.dim) (wf : Q.le rlo.val rhi.val)
      (h₁ : Q.le lo.val rlo.val) (h₂ : Q.le rhi.val hi.val) : ValueMeets (.rangeWithin rlo rhi) (.range lo hi)
  | atLeastMax {q m : Quantity} (d : m.dim = q.dim) (h : Q.le q.val m.val) : ValueMeets (.atLeast q) (.max m)
  | atLeastRange {q lo hi : Quantity} (d : hi.dim = q.dim) (h : Q.le q.val hi.val) : ValueMeets (.atLeast q) (.range lo hi)
  | atMostMin {q m : Quantity} (d : m.dim = q.dim) (h : Q.le m.val q.val) : ValueMeets (.atMost q) (.min m)
  | atMostRange {q lo hi : Quantity} (d : lo.dim = q.dim) (h : Q.le lo.val q.val) : ValueMeets (.atMost q) (.range lo hi)
  | flagIs {b : Bool} : ValueMeets (.flagIs b) (.flag b)
  | countAtLeast {n m : Nat} (h : n ≤ m) : ValueMeets (.countAtLeast n) (.count m)
  | countEquals {n : Nat} : ValueMeets (.countEquals n) (.count n)
  | enumIn {allowed : List String} {s : String} (h : s ∈ allowed) : ValueMeets (.enumIn allowed) (.enum s)
  | setContains {needed xs : List String} (h : ∀ x ∈ needed, x ∈ xs) : ValueMeets (.setContains needed) (.set xs)

ValueFails has the same eleven cases with the comparison negated. A value that is unknown, has the wrong units or the wrong shape satisfies neither, so it can only ever produce NEED INFO.

Layer 4, the definition of YES

/-- What ACCEPT is supposed to mean. -/
def AcceptSpec (cfg : Configuration) (e : Experiment) : Prop :=
  e.confirmed = true ∧
  (∀ r ∈ e.requirements, r.mandatory = true → r.applicable = true → ReqOK cfg e r) ∧
  (∀ c ∈ e.coupled, c.mandatory = true → c.applicable = true → CoupledOK cfg e c) ∧
  ((∃ r ∈ e.requirements, r.mandatory = true ∧ r.applicable = true ∧ ReqPasses cfg e r) ∨
   (∃ c ∈ e.coupled, c.mandatory = true ∧ c.applicable = true ∧ CoupledPasses cfg e c))

Correct is relative to this specification and to the sourced records. Lean does not prove that a datasheet is true or that the specification captures every physical effect.

Why it has to come out this way: proved in Lean

The tests above are measurements. lean/VsRegular.lean writes the checklist with CryoLean's own types and proves the pattern holds for every input, not just ours. It compiles 13 theorems against the unchanged checker, with Lean's standard axioms only.

A checker that is never wrong can only say YES where CryoLean does. If every YES a checker gives meets the specification, CryoLean says YES on that pair too, so no such checker decides more than CryoLean. sound_yes_le_cryolean, and the same for NO: sound_no_le_cryolean.
So every extra YES is unsupported. On the catalog the checklist says YES 14,558 times and CryoLean 3,118 times; each of the 11,440 extra YESes fails the specification. extra_yes_unsupported
The checklist approves a blank datasheet, for every experiment. CryoLean never does. checklist_yes_to_blank_sheet, cryolean_no_yes_to_blank_sheet
Hiding a line can flip the checklist from NO to YES (10 T magnetoresistance on the 9 T DynaCool). Hiding lines can never do that to CryoLean. checklist_not_monotone, hiding_lines_never_creates_yes
The checklist believes a guessed 14 T; CryoLean does not decide on it. checklist_believes_a_guess
Every line of the 50-qubit layout passes, and the heat budget still fails: 3 × 4.864 µW = 14.592 µW against 12 µW. The checklist says YES, CryoLean says NO. checklist_misses_coupled_physics, wiring_load_is_14592_nW
/-- The spec-sheet checklist: NO if some line visibly fails, otherwise YES. -/
def checklist (cfg : Configuration) (e : Experiment) : Verdict :=

What it costs

Being right costs very little. On the full catalog CryoLean answers NEED INFO 11,458 times, against 11,431 for the careful spreadsheet, and its result lists which lines are missing (in the hide-one-line test it named the hidden line every time). More research can only resolve those answers, never reverse a decided one (verdict_refines). The regular methods also said NO 22 times on the strength of an unsourced number or an unsourced "not fitted" claim; CryoLean waits for a source there too.

What this does not show

  • The truth in T1, T2 and T4 is the catalog's sourced record. If a datasheet is wrong, every method inherits the error.
  • T1 and T2 perturb real records. They measure what each method does with a silent or borrowed line, not how often real datasheets are silent.
  • The regular-way checkers are ours. They are short, readable and in the repo, and two of them already avoid the silent-line mistake, which is why all three are reported.
  • Floating point never flipped a verdict in these runs. The physics script's misses come from believing unsourced numbers.
  • No language-model baseline is included yet.
